## 核心概念

### 订阅的基本工作流程

```
PT站资源获取 → 缓存/识别 → 匹配所有订阅 → 过滤规则 → 自动下载
```

### 关键术语

| 术语 | 说明 |
|------|------|
| **订阅模式** | 决定如何获取PT站资源的方式 |
| **定时搜索** | 主动搜索每个订阅的补全机制 |
| **缓存** | 临时存储PT站种子信息 |
| **洗版** | 不断升级到更高质量版本 |
| **优先级规则** | 定义资源质量排序标准 |

---

## 三种订阅模式详解

MoviePilot 提供三种订阅模式，可以**同时启用**互为补充。

### 模式一：自动模式（spider）⭐ 推荐

**界面显示**：`订阅模式 → 自动`
**环境变量**：`SUBSCRIBE_MODE=spider`

#### 工作原理

```
定时爬虫(每天32次) → 爬取PT站首页前2页 → 缓存种子 → 所有订阅并行匹配
```

**代码实现**（`app/chain/torrents.py:230-247`）：
```python
# 爬取每个站点的前2页
for page in range(2):
    page_torrents = self.browse(domain=domain, page=page)
    torrents.extend(page_torrents)

# 取最新的N条（默认50，大内存模式100）
torrents = torrents[:settings.CONF.refresh]
```

#### 执行频率

- **每天32次**，随机分布在24小时内
- 平均约 **45分钟执行一次**
- 配置代码：`app/scheduler.py:267-280`

```python
# 生成32个随机时间点
triggers = TimerUtils.random_scheduler(num_executions=32)
for trigger in triggers:
    self._scheduler.add_job(
        hour=trigger.hour,
        minute=trigger.minute,
        func=SubscribeChain().refresh
    )
```

#### 优缺点

**✅ 优点**：
- 直接抓取站点首页，不依赖RSS
- 覆盖范围广（前2页所有种子）
- 执行频率高（每天32次）
- **所有订阅并行匹配**，效率高

**❌ 缺点**：
- 需要浏览器仿真对抗反爬
- 资源占用略高于RSS模式
- 可能需要配置 FlareSolver 等工具

#### 适用场景

- ✅ **默认推荐**，适合大多数用户
- ✅ PT站没有RSS或RSS质量不佳
- ✅ 追求全面覆盖，减少遗漏

---

### 模式二：站点RSS 模式

**界面显示**：`订阅模式 → 站点RSS`
**环境变量**：`SUBSCRIBE_MODE=rss`

#### 工作原理

```
定时RSS(可配置周期) → 读取PT站RSS订阅源 → 缓存种子 → 所有订阅并行匹配
```

**代码实现**（`app/chain/torrents.py:138-185`）：
```python
# 解析RSS订阅源
rss_items = RssHelper().parse(site.get("rss"))

# 组装种子信息
for item in rss_items:
    torrentinfo = TorrentInfo(
        title=item.get("title"),
        enclosure=item.get("enclosure"),
        pubdate=item["pubdate"]
    )
    torrents.append(torrentinfo)
```

#### 执行频率

- **可配置**，默认30分钟
- 界面选项：10分钟 / 20分钟 / 30分钟 / 1小时 / 12小时 / 1天
- 环境变量：`SUBSCRIBE_RSS_INTERVAL=30`

#### 优缺点

**✅ 优点**：
- 资源占用低，不需浏览器仿真
- 对PT站压力小
- 配置简单，稳定性高

**❌ 缺点**：
- **依赖RSS质量**，有些站点RSS更新慢或不全
- RSS通常**只包含最新种子**，旧资源可能不在RSS中
- 覆盖范围受限

#### 适用场景

- ✅ PT站有高质量RSS源
- ✅ 追求低资源占用
- ✅ 网络环境受限，无法使用浏览器仿真

---

### 模式三：订阅定时搜索（补全机制）⭐ 重要

**界面显示**：`订阅定时搜索` 开关
**环境变量**：`SUBSCRIBE_SEARCH=true`

#### 工作原理

```
定时任务(默认24小时) → 逐个订阅串行搜索PT全站 → 过滤 → 下载 → 1-5分钟延迟 → 下一个订阅
```

**代码实现**（`app/chain/subscribe.py:485-662`）：
```python
def search(self, sid=None, state='N', manual=False):
    # 获取所有订阅
    subscribes = subscribeoper.list(self.get_states_for_search(state))

    for subscribe in subscribes:
        # 随机延迟1-5分钟（避免站点压力）
        if not sid and state in ['R', 'P']:
            sleep_time = random.randint(60, 300)
            time.sleep(sleep_time)

        # 主动搜索PT站
        contexts = SearchChain().process(
            mediainfo=mediainfo,
            keyword=subscribe.keyword,
            sites=sites
        )

        # 自动下载
        DownloadChain().batch_download(contexts=contexts)
```

#### 执行频率

- **默认24小时**执行一次
- 可配置：`SUBSCRIBE_SEARCH_INTERVAL=24`

#### 关键特性

**🔍 主动搜索**：
- 不依赖缓存，直接去PT站全站搜索
- 能找到spider/rss模式遗漏的资源

**⏱️ 串行执行**：
- 每个订阅之间延迟1-5分钟
- 避免对PT站造成过大压力
- **如果订阅数量多，可能需要几小时才能全部执行完**

**计算示例**：
- 50个订阅 × 平均3分钟 = **约2.5小时**
- 100个订阅 × 平均3分钟 = **约5小时**

**🔒 锁机制**：
- 最长执行2小时后超时（`_LOCK_TIMOUT = 3600 * 2`）
- 防止长时间占用资源

#### 优缺点

**✅ 优点**：
- **全站搜索**，覆盖最全面
- 能补全spider/rss模式的遗漏
- 适合"旧剧补全"场景

**❌ 缺点**：
- 串行执行，耗时长
- 对PT站压力较大
- 订阅多时可能超时，后面的订阅无法执行

#### 适用场景

- ✅ **作为spider/rss的补充**
- ✅ 订阅数量适中（<50个）
- ✅ 发现有资源遗漏时启用

---

### 三种模式对比表

| 特性 | 自动(spider) | 站点RSS | 订阅定时搜索 |
|------|-------------|---------|------------|
| **执行方式** | 爬虫抓取首页 | 解析RSS源 | 主动全站搜索 |
| **执行频率** | 每天32次(~45min) | 可配置(默认30min) | 默认24小时 |
| **处理方式** | 所有订阅并行匹配缓存 | 所有订阅并行匹配缓存 | 逐个订阅串行搜索 |
| **抓取范围** | 每站前2页 | RSS源内容 | 全站搜索 |
| **延迟** | 无 | 无 | 1-5分钟/订阅 |
| **覆盖范围** | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| **资源占用** | 中 | 低 | 高 |
| **PT站压力** | 中 | 低 | 高 |
| **适用场景** | **默认推荐** | RSS质量好 | 补全遗漏 |

## 缓存机制与限制

### 缓存的作用

缓存种子信息，避免重复识别和处理，提高效率。

### 三层限制机制

#### 1️⃣ 爬取范围限制

**spider模式**（`app/chain/torrents.py:234-240`）：
```python
# 只爬前2页
for page in range(2):
    page_torrents = self.browse(domain=domain, page=page)
```

**影响**：如果目标资源不在PT站首页前2页，无法被抓取。

---

#### 2️⃣ 处理数量限制

**代码**（`app/chain/torrents.py:247`）：
```python
# 按发布时间排序，取前N条
torrents.sort(key=lambda x: x.pubdate, reverse=True)
torrents = torrents[:settings.CONF.refresh]
```

**限制值**（`app/core/config.py:718-735`）：

| 模式 | 每站处理数量 |
|------|------------|
| **普通模式** | 50条 |
| **大内存模式** | 100条 |

**环境变量**：`BIG_MEMORY_MODE=true`

---

#### 3️⃣ 缓存容量限制

**代码**（`app/chain/torrents.py:296-297`）：
```python
# 如果超过限制，移除旧种子（FIFO）
if len(torrents_cache[domain]) > settings.CONF.torrents:
    torrents_cache[domain] = torrents_cache[domain][-settings.CONF.torrents:]
```

**限制值**：

| 模式 | 每站缓存容量 |
|------|------------|
| **普通模式** | 100条 |
| **大内存模式** | 200条 |

**影响**：旧种子会被FIFO淘汰，即使之前抓取过也可能被移除。

---

### 缓存流程图

```
┌─────────────────────────────────────────────┐
│  PT站发布1000个种子                          │
└─────────────────┬───────────────────────────┘
                  │
                  ▼
┌─────────────────────────────────────────────┐

└─────────────────┬───────────────────────────┘
                  │
                  ▼

                  ▼

└─────────────────────────────────────────────┘
```

## 常见问题：为什么有些剧集没下载？

### 问题现象

> "PT站新发布的电视剧A已经下载了最新一集，但比A发布更早的电视剧B却没有下载最新一集。"

### 根本原因分析

#### ❌ 不是订阅执行顺序问题

spider/rss模式是**所有订阅并行匹配缓存**，不存在"先处理A后处理B"的情况。

#### ✅ 真正原因：缓存覆盖问题

**原因1：爬取时机**
- 电视剧B发布时间：12:00
- 爬虫执行时间：11:45（B还没发布）→ ❌ 未抓取
- 下次爬虫执行：12:30（B已被新种子挤出前2页）→ ❌ 仍未抓取

**原因2：缓存容量限制**
```
12:00 - B发布，被抓取并缓存 ✅
12:01~13:00 - PT站又发布了150个新种子
13:00 - 下次爬虫执行，缓存只保留最新100条
       → B被移除 ❌
```

**原因3：RSS模式的固有限制**
- RSS源通常只包含最新100条
- 如果B不在RSS源中 → 永远抓取不到

**原因4：处理数量限制**
```
抓取到300条种子
↓
只处理最新50条（普通模式）
↓
B在第60条 → 被跳过 ❌
```

---

### 解决方案

#### 🥇 方案一：启用订阅定时搜索（推荐）

**操作**：
```
订阅设置 → 订阅定时搜索 → ✅ 打开
```

**效果**：
- 每24小时主动搜索每个订阅
- 不依赖缓存，全站搜索
- 能找到spider/rss遗漏的资源

**适合**：所有场景，强烈推荐开启

---

#### 🥈 方案二：改为自动模式

**操作**：
```
订阅模式 → 自动（spider）
```

**效果**：
- 比RSS覆盖更全（爬取首页而非RSS源）
- 每天32次执行（比RSS的30分钟略频繁）

**适合**：RSS模式遗漏较多时

---

#### 🥉 方案三：启用大内存模式

**环境变量**：
```bash
BIG_MEMORY_MODE=true
```

**效果**：
- 缓存容量：100 → 200条/站
- 处理数量：50 → 100条/站
- 覆盖范围翻倍

**适合**：硬件资源充足

---

#### 方案四：组合配置（最佳效果）⭐

```
订阅模式：自动
订阅定时搜索：✅ 打开
大内存模式：✅ 开启
```

**效果**：
- 自动模式每天32次抓取（主力）
- 定时搜索每天1次全站搜索（兜底）
- 大缓存减少遗漏（保险）
- **三重保障，遗漏率最低**

## 洗版功能详解

### 什么是洗版？

**洗版（Best Version）** = 不断升级已下载的资源到更高质量版本

### 使用场景

```
Day 1:  下载《某剧》1080P             (优先级60)
Day 3:  发现4K版本 → 自动下载          (优先级80)
Day 7:  发现4K杜比视界 → 自动下载      (优先级95)
Day 30: 发现4K Remux杜比视界 → 下载   (优先级100，完成洗版)
```

---

### 洗版优先级规则

#### 作用

定义"什么算更高质量"的标准。

#### 示例规则

| 条件 | 优先级加分 | 说明 |
|------|----------|------|
| **分辨率** | | |
| 4K/2160P | +40 | 最高分辨率 |
| 1080P | +30 | 高清 |
| 720P | +20 | 标清 |
| **视频编码** | | |
| Remux | +20 | 无损原盘 |
| H.265/HEVC | +10 | 高压缩比 |
| H.264/AVC | +5 | 标准编码 |
| **HDR技术** | | |
| 杜比视界 | +15 | 最佳HDR |
| HDR10+ | +10 | 动态HDR |
| HDR10 | +5 | 基础HDR |
| **音频** | | |
| Atmos | +10 | 全景声 |
| DTS-HD MA | +8 | 无损音轨 |
| AC3 | +5 | 标准音轨 |

**总优先级 = 各项加分之和**

---

### 洗版特殊逻辑

**代码**（`app/chain/subscribe.py:595-606, 1016-1021`）：

```python
# 1. 洗版时，电视剧必须是整季
if subscribe.best_version:
    if torrent_mediainfo.type == MediaType.TV:
        if torrent_meta.episode_list:  # 有集数列表 = 非整季
            logger.info(f'{subscribe.name} 正在洗版，{torrent_info.title} 不是整季')
            continue  # 跳过

# 2. 洗版时，只下载优先级更高的资源
if subscribe.best_version:
    if subscribe.current_priority and torrent_info.pri_order <= subscribe.current_priority:
        logger.info(f'{subscribe.name} 正在洗版，{torrent_info.title} 优先级低于或等于已下载优先级')
        continue  # 跳过

# 3. 达到优先级100时，洗版完成
if priority == 100:
    logger.info(f'{mediainfo.title_year} 洗版完成')
    self.__finish_subscribe(subscribe)  # 完成订阅
```

---

### 两种优先级规则组

| 规则组 | 用途 | 策略 |
|--------|------|------|
| **订阅优先级规则组** | 普通订阅 | 下载"足够好"的版本就停止 |
| **洗版优先级规则组** | 洗版订阅 | 追求完美版本（优先级100） |

---

### 洗版注意事项

#### ⚠️ 代价

- **流量消耗大**：同一剧集可能下载多次
- **磁盘占用高**：新旧版本可能同时存在
- **时间成本**：可能等待数月才有完美版
- **PT站压力**：需要保持做种

#### ✅ 适合洗版

- 喜欢的经典剧集/电影
- 家庭影院/高端播放设备
- 有足够存储空间和带宽
- PT站上传需求大

#### ❌ 不适合洗版

- 普通追剧
- 存储/带宽有限
- 只是看个热闹

### RSS周期建议

| 周期 | 评价 | 适用场景 |
|------|------|---------|
| 10分钟 | ⚠️ 不推荐 | 可能被PT站限流 |
| 20分钟 | 🤔 可选 | 追求极致响应速度 |
| **30分钟** | ✅ **推荐** | **最佳平衡** |
| 1小时 | ⏱️ 可接受 | 资源受限 |
| 12小时+ | ❌ 不推荐 | 遗漏率高 |

**建议**：保持30分钟即可，更短收益不明显且风险大。

## 问题排查清单

### 症状：某个剧集一直没下载

#### 排查步骤

**1️⃣ 检查订阅状态**
```
订阅页面 → 查看该订阅 → 确认状态为"订阅中(R)"
```
- 如果是"暂停(S)" → 恢复订阅
- 如果是"完成" → 检查是否误判为已完成

**2️⃣ 检查媒体库**
```
检查文件系统资源：✅ 开启时
→ 系统会先检查媒体库是否已存在
→ 已存在会自动完成订阅
```
- 确认媒体库中是否已有该剧集
- 如果有但想重新下载 → 关闭"检查文件系统资源"

**3️⃣ 查看日志**

**关键日志关键词**：
```bash
# 订阅刷新日志
"开始匹配订阅，标题：XXX"
"XXX 匹配完成，共匹配到N个资源"
"XXX 未匹配到符合条件的资源"

# 定时搜索日志
"开始搜索订阅，标题：XXX"
"订阅搜索随机休眠 120 秒"
"XXX 未搜索到资源"

# 缓存日志
"站点 XXX 有 50 个新种子"
"站点 XXX 没有新种子"
```

**分析日志**：
- 如果没有"开始匹配订阅" → 订阅未被执行
- 如果有"未匹配到符合条件" → 缓存中无符合的资源
- 如果"未搜索到资源" → PT站确实没有

**4️⃣ 手动搜索验证**

```
订阅页面 → 点击该订阅的"搜索"按钮
```
- 会立即执行全站搜索
- 查看是否能搜索到资源
- 如果能搜到 → 说明自动模式有遗漏，建议开启定时搜索
- 如果搜不到 → PT站确实没有该资源

**5️⃣ 检查站点配置**

```
站点管理 → 查看订阅涉及的站点
```
- 确认站点已启用
- 确认站点Cookie未过期
- 确认订阅中指定的站点正确

**6️⃣ 检查过滤规则**

```
订阅详情 → 查看过滤条件
```
- 分辨率、质量、编码等过滤是否过严
- 尝试放宽条件

#### 原因

**减少订阅数量**：
- 删除已完成的订阅
- 暂停不急的订阅

**缩短搜索间隔**：
```bash

```
虽然单次时间长，但更频繁执行

**手动触发重要订阅**：
```
订阅页面 → 点击"搜索"按钮
```

### 症状：PT站报错429（Too Many Requests）

```bash

# 修改代码：app/scheduler.py:269

```

**配置浏览器仿真**：
```bash
BROWSER_EMULATION=flaresolverr
FLARESOLVERR_URL=http://127.0.0.1:8191
```

**检查站点配置**：
- 站点管理 → 查看请求间隔设置
- 增加延迟时间

## 总结

### 核心要点

1. **三种模式可以同时启用**，互为补充
2. **自动(spider)模式**是默认推荐，覆盖最全
3. **订阅定时搜索**是重要的兜底机制，强烈建议开启
4. **缓存有三层限制**：爬取范围、处理数量、缓存容量
5. **洗版**适合精选内容，不适合大量订阅
6. **大内存模式**能有效减少遗漏
